When a tison-generated parser produces a confusing "Unexpected token X, expected Y" error that doesn't match the obvious grammar reading, pure reasoning about the grammar repeatedly turned out wrong or too slow — the user's preferred and effective approach is **direct empirical inspection of the generated tables/trace**, not guessing from the grammar source.

**Why:** tison is LALR(1) (see [[tison-project]]), which merges states with identical LR(0) cores, so wrong parses are often caused by a shift/reduce conflict between two *seemingly unrelated* rules that happen to share an LR(0) state, silently resolved by defaulting to shift. The actual colliding rule pair is almost never the one you'd guess first from reading the grammar.

**How to apply — the technique that worked every time:**
1. Add a temporary trace line in `runParser`'s main loop (`src/tison.ts`), gated behind `(globalThis as any).TISON_TRACE`, logging the token, action kind, and current state at each step.
2. Write a tiny one-off script in `examples/_reproN.ts` (numbered, throwaway) that sets `(globalThis as any).TISON_TRACE = true`, imports the parser, and parses a *minimal* failing snippet (bisect the real failure down to the smallest repro first — this matters a lot, large inputs make the trace unreadable).
3. Run it, find the state where the trace goes wrong (often "shift" where you expected "reduce", or vice versa, right before the actual failure).
4. From a second scratch script, import `tsParser`/`jsParser` etc. directly and dump `tables.action[N]` for the suspect state, `tables.conflicts.filter(c => c.state === N)`, and `tables.rules[ruleId]` to identify exactly which two rules are colliding and how the conflict was resolved.
5. Delete the `_reproN.ts` scratch files and remove the trace line again before finishing — don't leave debug instrumentation committed.

Confirmed effective for: the `angleBracket`/`type_arguments` over-broad-terminal bug, the `property_assignment`/`object_pattern_property` shift-reduce conflict, and the ternary-`?`/optional-parameter-`?` ambiguity. In every case, the conflict was real (visible in `tables.conflicts`) and the fix followed directly once the exact rule pair was known — the hard part was finding the pair, not fixing it.

**A second failure class exists that this technique doesn't catch: performance blowups (hangs/near-infinite loops), not wrong parses.** Found twice in one session (2026-07-02, see [[tison-project]]'s `test_tar.ts`/`cvinfo.ts` rows): a genuine infinite loop from an ERROR token not advancing lexer position, and a combinatorial blowup from `WS`'s ASI-check `lex.next()` peek cascading across many consecutive comment lines. Neither shows up in `tables.conflicts` (that's a parser-table concept; these are lexer/runtime issues) and neither responds to the trace-line technique above (the trace would just show the same state/token forever — informative that it's *not* making progress, but not *why*). What worked instead:
1. Never trust a bare `sleep N && check` loop or a `perl -e 'alarm N; exec ...'` wrapper to reliably kill a hung process — `exec` replaces the process image and the alarm's signal handler goes with it. Use a mechanism that actually owns/tracks the child (the harness `Bash` tool's own `timeout` parameter, or Node's `child_process` `{timeout: N}` option) so a hang is reliably killed and reported instead of silently eating CPU in the background.
2. Bisect the *input*, not the code: take the real file that hangs, cut it down (or synthesize a minimal analog) while checking each candidate against a hard timeout, varying one dimension at a time (size vs. structure vs. specific content) until a minimal repro falls out. For `cvinfo.ts` this meant ruling out "large object literal" (fast even at 100 entries) and "comments interleaved with code" (fast) before landing on "many *consecutive* comment-only lines" (instant hang even at 10) — the dimension that mattered wasn't the one that looked most suspicious at first (object literal size).
3. Once isolated, explain the *mechanism*, don't just find a regex that happens to fix the symptom — the first fix for the EOF-comment bug (a lookahead so the comment terminal wouldn't consume its own trailing newline) "fixed" that bug but silently created the `cvinfo.ts` regression by changing how often `WS`'s expensive peek callback fires. The actual correct fix (`\n?`, optional-but-still-consumed) was less clever and didn't touch `WS`'s triggering conditions at all.

A third hang (2026-07-02, `dwg/hidden/dwg_reader copy.ts` — genuinely corrupted source with a stray unmatched `}`) turned out to be the *same* underlying flaw as the first (`jsRecover` synthesizing a token that never consumes the real one, so recovery re-fires forever), just via a different trigger condition (`remaining.startsWith('}')` instead of the EOF-comment case). Since that's now two distinct triggers of one flaw in a single session, fixed it at the engine level in `runParser`/`runGlrFork` (`src/tison.ts`) instead of patching a third specific trigger: track whether the lexer's `stream.offset` has actually advanced across repeated recovery invocations, and throw a clear error if it hasn't after a generous bound. **The first attempt at this safeguard had its own bug worth remembering**: it reset the stuck-counter on every non-recovery step, which never actually triggers, because a stuck recovery cycle *alternates* recovery steps with genuine shift/reduce of the synthesized token itself (insert phantom `;` → shift it → reduce to empty-statement → recovery again) — so two recovery steps almost never land back-to-back even when genuinely stuck forever. The fix was to compare against `stream.offset` directly (has the *real* position moved since recovery last fired) rather than "was the immediately-previous step also recovery" — the latter is a plausible-looking proxy that doesn't actually track the thing that matters.

**Fourth class found 2026-07-03/04: a "missing transition" bug that looks exactly like a conflict but ISN'T one, and `forceFork` cannot fix it.** Symptom: `static load(): void;` (a bodyless class method_signature with a sole `static` modifier) failed to parse, standalone, with every other modifier-count/member-shape combination working fine. Two plausible-looking fixes were tried and both **empirically failed to change the failure at all** (proof, not guesswork, that they were wrong): (1) a dedicated `STATIC_BLOCK_START` terminal with a lookahead regex, on the theory that `static_block` and the modifier-list path were colliding via state-merging — implemented, typechecked, ran the exact same failing repro, identical failure. (2) tagging js-parser.ts's `Rule(['static', class_member_body])` with `forceFork`, on the theory that a shift/reduce conflict was picking the wrong branch — implemented, typechecked, same repro, identical failure. **The check that proved (2) could never have worked**: searched `tables.conflicts` for any entry referencing the relevant rule IDs — there were ZERO. `forceFork`/`assoc:'fork'` only changes how `setAction` *resolves a recorded conflict*; LALR(1) state-merging by LR(0) core item sets can eliminate the needed item (and thus the transition) from a state entirely, with no conflict ever recorded to resolve, because the state that would've had it got merged into one where the item is simply absent. **Rule of thumb: before reaching for `forceFork`/`WithPrec` on a "missing transition"-shaped bug, grep `tables.conflicts` for the suspect rule IDs first — if it's empty, the fix has to be a grammar-shape change (a new/direct rule alternative), not a precedence/fork tag, no matter how conflict-like the symptom looks.** The actual fix here (see [[tison_project]]) was adding a new direct rule giving `static` its own path to `class_member_overloads`, symmetrical to js-parser.ts's existing direct path to `class_member_body` — once the missing production existed, ordinary one-token lookahead disambiguated it with zero new conflicts recorded.

**Refinement (2026-07-10, `() => ({})` fix, see [[tison_project]]): "missing transition, `forceFork` can't fix it" describes ONE missing item, not a whole class of bugs that's permanently unfixable by `forceFork`.** The `() => ({})` bug had the exact same signature as the `static` case above (empty `tables.conflicts` for the relevant state) — `object_literal`'s empty-`{}` case reduces via a zero-width `MaybeList`-empty item that never made it into a state shared with `object_pattern`'s own literal `Rule(['{','}'])`. Adding a brand-new, literal `Rule(['{','}'])` alternative directly to `object_literal` (matching `object_pattern`'s shape, redundant with the existing `MaybeList`-based rule whenever reached alone) didn't just restore the missing path — because it's now a genuine *second complete item* colliding with `object_pattern`'s at the same state (not one item present, one silently absent), it registered as a real, recorded reduce-reduce conflict, which `WithPrec(rule, forceFork)` then legitimately resolved via GLR. **So the actual rule of thumb is narrower than it first looked**: check `tables.conflicts` before reaching for `forceFork` on the *existing* rules (still true, still saves time) — but if the fix route is "add a new rule for the missing interpretation," check afterward whether that new rule creates a genuine two-item collision (conflict-shaped) instead of just restoring a single missing item (still-invisible-to-forceFork-shaped); if it's the former, `forceFork`/`WithPrec` on the new rule is back on the table and is usually simpler than hand-crafting a disambiguating direct path.

**Fifth item (2026-08-21): the `$error`/ERROR terminal's meaning is state-relative, not global — don't gate recovery on `tok.type === ERROR` alone.** While root-causing why [[tison_project]]'s new official-TypeScript-test harness (`test/test-ts-official.ts`, runs tison's TS parser+checker against the real `tests/cases/compiler`+`conformance` corpus from a local TypeScript checkout) hit the "Parser/GLR fork stuck in error recovery" safeguard (itself from the third hang above) on 428 of ~13.5k files, first instinct was: an ERROR token means "no terminal anywhere in the grammar matches this character," so recovery (`recover()`, the ASI-`;`-insertion heuristic in js-parser.ts) can never help and should be skipped outright when `realTok.type === ERROR`. **That's wrong and broke real ASI** — `nextToken` lexes only against `allowed = tables.action[currentState]` (the *current parser state's* permitted terminal set), so ERROR also fires for a perfectly real, elsewhere-lexable token that just doesn't fit *this* state (e.g. `x = 1\nvar y` — `var` is ERROR at the assignment-expression continuation state, and ASI recovery inserting `;` and shifting to a new state is exactly what's supposed to resolve it by making the *next* lex attempt, against the new state's allowed set, succeed). Gating `usingRecovery` on `realTok.type !== ERROR` silently disabled that path; caught immediately because `test/test-js-parser.ts`'s own ASI cases (regression-tested before/after, per [[feedback_no_git_stash_midsession]]-style discipline of verifying against the working tree) started throwing `Unexpected character 'v'` instead of parsing. **The actual fix, once the safeguard's real job was reconsidered**: the existing `MAX_RECOVERY_AT_SAME_OFFSET`/`MAX_RECOVERY_PER_POSITION` stuck-counters (from the third-hang fix above) were already correctly discriminating real stuck-forever loops from legitimate 1-step ASI resolutions — the only thing wrong was what happened *once the cap tripped*: throwing a bespoke "stuck in error recovery ... this is a parser/grammar bug" message, when for the TS corpus the overwhelming majority of trips are on fixtures that are *deliberately* malformed (testing tsc's own diagnostics: stray `\`, mid-file shebangs, `@dec` on a non-decoratable declaration, literal `¬` bytes) — not grammar bugs at all. Fix: on cap trip, set `usingRecovery = false` for that iteration only (leave the trigger/timing untouched) so it falls through to the same ordinary `Unexpected token/character` throw every other syntax error uses, instead of a separate alarming message. Same idea applied to `runGlrFork`'s per-path cap and its "No active GLR fork paths survived" fallback (added an `ERROR`-specific branch there producing the plain message too). Net effect: same non-termination guarantee, same trigger conditions, just an honest diagnostic instead of an overclaiming one — reclassified ~398 of 428 self-flagged "bugs" as ordinary (and often intentional) invalid-input reports, with zero behavior change on any input that previously succeeded (confirmed via full `test-js-parser.ts`/`test-tison.ts` reruns matching baseline output exactly).

**Sixth class (2026-08-22, decorator-support work, see [[tison_decorator_support]] for the full story): a grammar addition that's individually correct can silently corrupt ASI recovery in a totally unrelated, far-away construct, via LALR state-sharing — and this shows up as a runtime bug (misclassified token), not a `tables.conflicts` entry, so the earlier "check conflicts first" technique doesn't catch it.** Adding decorator support to class *members* (`Rule([decorator_list, class_member_body], ...)`, referencing the leaf `class_member_body` from a new position) broke `var a = 1\nvar b = 2` (no semicolons) — the second `var` got contextually mis-lexed as a plain `identifier`, because `class_member_body`'s field-assignment shape (`key '=' assignment_expression ';'`) is structurally identical to an ordinary variable declarator, so states built from it were *already* LALR-merged with statement-level parsing states before this change; reaching that shared territory from a new grammar position shifted the merge boundary, and `VAR` stopped being a valid lexer candidate at the exact state used mid-way through the (unrelated) ASI reduce-cascade. Since tison lexes a token once per position using the *current* state's allowed set and never re-lexes across subsequent reduces, the misclassification was permanent once it happened. **Two structurally different wiring shapes were tried (self-referencing the whole `class_member`, and a non-recursive pair referencing `class_member_body` twice) and both broke it identically** — proving the fragility is about reaching that already-overloaded nonterminal from a new position at all, not about recursion shape. **Diagnostic method that worked**: bisect by disabling every new-consumer rule one at a time (not "disable one, leave the rest" — that still triggers if *any other* consumer alone is also guilty; test genuinely alone) until the minimal guilty rule is found, then use the same cache-bypass-`makeDebug()` + `tables.lr0States`/`.action[state]` dump technique to confirm the mechanism (checked the specific state's allowed-terminal-set directly: `VAR` was absent, `IDENT` present, explaining the misclassification). **Rule of thumb this adds to the catalog**: before adding a new rule that references an *existing, already load-bearing* nonterminal from a *new* grammar position — especially one whose item shape structurally overlaps something used elsewhere (assignment-shaped class fields vs. var declarators, in this case) — test far-away, structurally-unrelated constructs (plain `var`/ASI cases are a good canary) after the change, not just the construct you're adding support for. A clean typecheck and a passing targeted test are not enough; this class of bug only shows up in inputs that never mention the new syntax at all.

**Seventh item (2026-08-22, same-session follow-up: the "real fix" attempt for the sixth class, see [[tison_official_ts_test_suite]] item 15 for the full writeup) — a targeted engine-level fix that passes every hand-picked canary can still be a net regression at corpus scale, and the only way to catch that is to actually run the corpus.** Tried a `relexAt` mechanism: re-lex the stale lookahead token under the *current* (wider) state's row right before recovery triggers, adopting the result if it reclassifies. Two real bugs in the mechanism only surfaced once run against the full ~13.5k-file corpus, not against the `var a=1\nvar b=2`/decorator canaries that had been the only verification up to that point: (1) the adoption check didn't exclude a failed re-lex (`ERROR`), so re-lexing a token that was *already correctly classified* but legitimately unmatched at this state (e.g. `}` needing ASI first, since ASI lives in `recover()` not the grammar) would re-lex to `ERROR` and get adopted anyway, destroying a valid token — this alone broke 324 real files, dominated by one extremely common shape (`(function(){ return x});`, an IIFE as a block's last ASI'd statement). (2) fixing that surfaced a second bug: the position-restore-on-no-change logic only fired when the re-lex reproduced the *same* type, not when it failed — since a failed lex never advances the stream offset, this silently left the stream rolled back to the token's start instead of its end whenever adoption was correctly declined. **Even after fixing both, corpus-scale testing showed a net regression (2,376 → 2,589 threw, +213) and, on closer trace, the fix didn't even solve its own target case** (the misclassified `var` kept re-lexing to `ERROR` under every state visited across the recovery loop, never finding a state that accepted `VAR`) — contradicting the premise verified by the small-scale canary. Reverted entirely. **Rule of thumb this adds**: for any change to shared lexer/recovery machinery, the fast targeted regression suite and a couple of hand-picked canaries are necessary but not sufficient — run the full official-corpus check (`test-ts-official.ts`) before trusting the change, since the failure modes that matter (here: an extremely common but easy-to-not-think-of ASI-before-`}` shape) can be invisible to any canary set chosen by reasoning about the mechanism rather than by exhaustive real-world coverage.

**Eighth item (2026-08-23, long-tail triage continuation, see [[tison_official_ts_test_suite]] item 21 for the full writeup) — "the failing token's name" isn't always the terminal it visually is, and a `recover()` check written against one manifestation of that can silently miss another.** Item 7 fixed ASI-before-`}` by checking `lex.token.name === '}'` (the failing terminal's own name) instead of `lex.remaining.startsWith('}')` — correct for the case that prompted it. But a *different* ASI-before-`}` shape (`class A { a }`, a bare terminatorless class field) still failed, because in `class_member_body`'s narrow state, `}` isn't even a lex *candidate* at all (only `(`/`;`/`=`/`:` are tried), so the lexer can't classify it as `}` — it comes back `$error` instead, and `lex.token.name === '}'` can never match an `$error` token. Found via a temporary `DEBUG_RECOVER` print (`console.error` inside `recover()` itself, removed after) showing `tokenName: '$error'`, not `'}'`. The fix layers a second check rather than replacing the first: for an `$error`-classified failing token specifically, `lex.remaining` *does* still start with the literal failing character (an ERROR token never advances the stream, unlike a real classified one) — so `lex.token.name === '$error' && lex.remaining.startsWith('}')` catches this second shape. **Rule of thumb**: "the failing token's name/type" is a single, narrow signal that only covers positions where the failing character *can* be classified as the terminal it looks like; a state where that terminal isn't even a candidate produces `$error` instead, and needs its own explicit check against the raw remaining text — don't assume one `recover()` condition generalizes across every state that superficially "fails on the same character."

**Ninth item (2026-08-23, long-tail triage, investigated but deliberately NOT fixed — see
[[tison_official_ts_test_suite]]'s "Investigated, NOT fixed" note): a locally-valid shift can permanently mask
a later failure from ever reaching `recover()`/ASI at all, and this class can't be fixed by any `recover()`
condition or grammar widening — it needs the ambiguity exposed as a real GLR fork.** All of this session's
earlier ASI gaps (items 7, 21, and the "eighth item" above) shared one shape: the failing token had *no*
valid action at all in the current state (`!direct || direct.kind === 'error'`), which is exactly the
condition that triggers `recover()`. This one doesn't: `class C { m(x): boolean\n [k: number]: string }`
(bodyless overload signature, ASI before the next member's `[`) — `[` right after the return type has a
*locally valid* direct shift, because it's a legitimate first step toward the array-type suffix `boolean[]`.
Confirmed via a temporary debug print in `runParser`'s shift branch (`tison.ts`, removed after): `[` shifts
normally (`isRealTok: true`, no recovery path taken at all), and the parser only discovers the interpretation
was wrong two tokens later, at `identifier ':'` — by which point it's already committed, and `recover()` never
ran because there was never a first-failure moment for it to run at. **Diagnostic method that worked**: the
established `console.error` debug-print-in-the-hot-path technique, this time in `runParser`'s `shift` branch
directly (not `recover()` itself, since the bug is about recovery never being *reached*) — logging
`tok`/`realTok`/target state at every shift, then reading the trace to see exactly which state committed to
which interpretation and when. **Rule of thumb this adds**: before assuming an ASI/recovery gap is fixable by
adjusting `recover()`'s conditions or widening a grammar rule in place, check whether the failing construct's
first token even reaches the `!direct || direct.kind === 'error'` branch at all — if it has *any* valid shift
from the state in question (even one that's ultimately a dead end further downstream), recovery is
structurally unreachable, and the real fix has to happen at the table/conflict level (a genuine GLR fork
between the two competing interpretations), not in `recover()`'s decision logic.
